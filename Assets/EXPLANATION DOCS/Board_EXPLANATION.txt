BOARD.CS - AUTHORITATIVE PLACEMENT AND RESOLUTION EVENTS
========================================================

What Board already did
----------------------
Board is the authoritative owner of the grid. It validates cells, registers a Box,
starts UniversalSodaTransferSystem, removes packed/empty boxes, and unlocks input
after the asynchronous resolver finishes. Those responsibilities and the current
transfer algorithm were preserved.

Why Board needed integration events
-----------------------------------
The Tutorial needs to distinguish two different moments:

1. A drop is accepted and the Box is registered in a grid cell.
2. Every soda transfer, animation, Match, removal, and cleanup caused by that
   placement has finished.

The old Tutorial inferred both moments from transforms and spawnedBoxes. That is
not reliable because a Box can be accepted immediately but continue resolving for
several frames. Board now publishes the two authoritative facts directly.

BoardPlacementAcceptedEvent
---------------------------
This public struct is a snapshot containing:

- Box: the accepted Box reference. It is alive when this event is raised.
- StableId: the ID assigned by Box.MarkPlaced.
- PlacementOrder: a monotonically increasing token for correlation.
- Column and Row: the actual cell accepted by Board.

The readonly fields make the payload informational. Subscribers cannot change the
Board by mutating the event data.

BoardPlacementResolutionEvent
-----------------------------
This public struct reports the later completion boundary:

- TriggerStableId: the ID of the Box that initiated this resolution.
- PlacementOrder: the same placement token used by the acceptance event.
- PackedMatches: how many packed boxes were retired during this resolution.
- IsBoardEmpty: the final Board state after cleanup.

Tutorial code correlates PlacementOrder rather than comparing world-position
distance. This completely removes the old 0.1 versus 0.155 offset problem.

New Board events
----------------
PlacementAccepted is a System.Action<BoardPlacementAcceptedEvent>.
PlacementResolutionCompleted is a
System.Action<BoardPlacementResolutionEvent>.

They are neutral gameplay events. Board never references TutorialManager or
SortingTutorialController, so normal levels do not depend on Tutorial code.

Exact acceptance order in UpdateBoxPosition
--------------------------------------------
For a valid placement, Board now performs this order:

1. Validate the Box capacity and soda count.
2. Store the Box in allBoxes and mark the Node occupied.
3. Move the Box to GetPlacementWorldPosition. This includes placedBoxYOffset.
4. Call MarkPlaced, assigning StableId and PlacementOrder.
5. Add the Box to boardBoxes if necessary.
6. Update lastPlacedBox and IsBoxRemoved.
7. Raise PlacementAccepted exactly once.
8. Remove the object from SpawnContoller.spawnedBoxes, which remains the live rail
   list.
9. Clear currentBox and start ResolvePlacement.

Raising the event after grid registration means a listener can safely read the
accepted coordinates. Raising it before the live-list removal does not make the
Tutorial depend on that list; the event payload contains everything it needs.

Exact resolution order in ResolvePlacement
-------------------------------------------
ResolvePlacement captures the trigger StableId, PlacementOrder, and current packed
Match sequence before doing asynchronous work. It then:

1. Sets IsResolving true, which makes CanInteract false.
2. Yields through UniversalSodaTransferSystem.Resolve.
3. If the resolver component is unexpectedly missing, logs a warning and still
   closes the lifecycle cleanly.
4. Waits until every adjacent blocked-cell break started by this resolution has
   completed and created its playable Node.
5. Cleans boardBoxes, evaluates Board-full state, and refreshes the UI.
6. Sets IsResolving false.
7. Calculates the packed-Match delta.
8. Raises PlacementResolutionCompleted exactly once.

The completion event is deliberately last. A Tutorial can begin its next Hand
instruction immediately after receiving it because Board input has already been
unlocked and all resolver animation waits have completed.

How packed Matches are counted
------------------------------
packedMatchSequence is incremented inside RetireBox only for packed=true. It is
placed after retiredBoxes.Add succeeds. retiredBoxes is the existing exactly-once
guard, so the same Box cannot increment the Match sequence twice.

Each ResolvePlacement records the sequence before and subtracts it from the value
after resolution. System.Math.Max protects against a negative value if a future
reset is introduced incorrectly. This reports Match facts without changing any
transfer decision.

ClearBoard changes
------------------
ClearBoard now also resets placementSequence, packedMatchSequence, and nextStableId.
This produces a fresh correlation timeline when the Board is deliberately cleared.

What was intentionally not changed
----------------------------------
- CanPlaceAt and cell validation.
- Board placement coordinates and placedBoxYOffset.
- UniversalSodaTransferSystem decisions.
- Packed/empty retirement animations.
- Rewards and truck-copy behavior.
- Removal from the live rail list.
- Hammer and Swap integration.
- The inactive historical code inside #if false.

Normal-level safety
-------------------
C# events do nothing when they have no subscribers. Therefore Level 1 continues
through the same Board path with only two inexpensive null event invocations and a
counter update when a Match occurs.

Adjacent-highlight placement constraint extension
-------------------------------------------------
The restoration adds a neutral, owner-scoped optional placement predicate.
TrySetPlacementConstraint(owner, predicate) refuses null arguments and refuses to
replace another owner's active constraint. ClearPlacementConstraint(owner) only
clears the predicate for the same owner. HasPlacementConstraint tells Box whether
a controller currently owns persistent cell highlights.

SortingTutorialController registers the predicate when its Tutorial starts and
clears it during lifecycle cleanup. TryPlaceBox first requires CanPlaceAt and then
requires this predicate when one exists. The predicate is absent in normal levels,
so CanPlaceAt remains their only placement rule.

Dynamic per-level layout extension (Phase 1)
--------------------------------------------
Board width and height remain serialized on each scene, but Board now also stores
removedCells. RebuildLayoutCache converts that list into a fast HashSet, and
IsPlayableCell is the shared shape rule. GenerateBoard skips removed coordinates,
adjacency excludes them, drop validation treats them as unavailable, and
CheckBoardFill counts only real Nodes. BoardEditor displays the shape as a visual
green-O/dark-X grid so level designers do not edit coordinates or code manually.

GetFirstPlayableNode and GetPlayableNodesSerpentine remove the clear tool's old
dependency on fixed cells such as grid[0,0] and grid[3,4]. See
DYNAMIC_BOARD_LAYOUT_EXPLANATION.txt for setup steps and regression tests.

Per-level initial Box extension (Phase 2)
-----------------------------------------
Board.initialBoxes is a sparse serialized list: only cells that begin occupied
have an InitialBoardBoxData entry. Each entry stores its coordinate, an optional
Box prefab override, and an ordered list of the existing Soda.SodaColor enum.
Missing entries mean empty cells, so large Boards do not allocate configuration
objects for every coordinate.

GenerateInitialBoxes runs after GenerateBoard. It reuses SpawnContoller.boxPrefab
when no override is assigned, reads capacity from the real Box SodaPosition
slots, creates Soda objects with Soda.SetColor, and registers the result through
the same allBoxes, boardBoxes, Node.isOccupied, and Box.MarkPlaced state used by
normal gameplay. It does not invoke placement events or start the resolver,
because loading a level is not a player move. See
INITIAL_BOX_LEVEL_SETUP_EXPLANATION.txt for the editor workflow and safety rules.

Scene preview and removed-cell visuals
--------------------------------------
BoardEditor registers DrawLayoutGizmos with Unity's DrawGizmo system. Playable
cells are translucent green cubes and removed cells are solid brown cubes. The
loop uses the configured width and height and is not limited to 20 cells.

GenerateRemovedCellVisual creates one collider-free brown GameObject for every
removed coordinate during GenerateBoard. Designers may assign a prefab/material,
or leave both empty for an automatic URP-compatible Cube. These objects are visual
feedback only; IsPlayableCell and CanPlaceAt remain the gameplay authority.

Breakable blocked-cell extension
--------------------------------
The existing removedCells data now represents cells that begin blocked. This
reuses the established shape data, lookup HashSet, brown visuals, Node prefab,
occupancy arrays, and match resolver instead of adding a parallel blocker system.

Board keeps removedCellVisuals, a Dictionary from Vector2Int to the generated
brown GameObject. The dictionary lets a match animate and destroy the exact
visual in constant time. breakingBlockedCells is a HashSet used as an exactly-once
guard when multiple packed Boxes touch the same blocker.

Only RetireBox(box, packed: true) starts blocker removal. NotifyBoxRemoved is used
by other removal paths such as tools, and empty source Boxes are retired with
packed=false; neither path unlocks blockers. This is why a Hammer deletion or an
empty transfer source cannot accidentally behave like a completed match.

BeginUnlockAdjacentBlockedCells checks the shared DirectOffsets array. It does
not call GetAdjacentPositions because that public method deliberately filters out
blocked cells. The raw offsets allow Board to find a blocked coordinate while
still enforcing bounds and orthogonal-only rules.

Update: BreakBlockedCellRoutine now also shakes the box with a damped jitter and
fires a dust-and-confetti burst once the shrink completes, and blocked boxes get
a generated packing-tape cross taped over their lid. The unlock state transition
below is unchanged. See BLOCKED_CELL_BOX_AND_BREAK_VFX_EXPLANATION.txt.

BreakBlockedCellRoutine scales the visual toward zero. A scale break works with
the generated opaque material and with custom prefabs, so no transparent shader
or extra material instance is required. `blockedCellBreakDuration` is serialized,
Inspector-configurable, and clamped to zero or greater in OnValidate.

UnlockBlockedCell performs the authoritative state transition:

- remove the coordinate from removedCellLookup and runtime removedCells;
- remove and destroy the matching brown visual;
- clear allBoxes at that coordinate;
- instantiate the existing Node prefab through CreatePlayableNode;
- mark that Node unoccupied and clear its highlight;
- remove the coordinate from breakingBlockedCells.

CreatePlayableNode is also used by GenerateBoard, which prevents startup and
runtime-unlock Node setup from drifting apart. The new Node automatically becomes
visible to drop detection, placement highlighting, occupancy checks, Board-full
logic, and subsequent neighbour queries because those systems already read grid
and removedCellLookup live.

ResolvePlacement waits while breakingBlockedCells is non-empty. This keeps
CanInteract false until the animation and state transition finish, and guarantees
PlacementResolutionCompleted describes the final unlocked layout.

Per-level Orders data (Orders feature, Phase 1)
-----------------------------------------------
Board now also stores this scene's Orders list, the per-color goal that will
replace the flat GameDataManager.boxNum >= 10 win condition.

levelOrders
    Serialized List<LevelOrderData> under a "Per-Level Orders" header, saved in
    the scene beside removedCells and initialBoxes. It is authored through the
    new Orders section of BoardEditor rather than as a raw array.

LevelOrders
    Public IReadOnlyList accessor. Read-only on purpose: the runtime manager
    copies these values into its own counters at level start, so retrying a
    level always restarts from the authored numbers instead of whatever the
    previous attempt left behind.

CountInitialSodasOfColor(color)
    Counts the sodas of one color that this level places on the board before the
    player acts. Only the inspector calls it, to warn a designer when an order
    asks for more of a color than the starting layout can supply.

No existing Board behavior changed in this phase. Placement, resolution,
packing, rewards, and the current CheckWinCondition call were left untouched, so
the addition is safe to import on its own. Full detail lives in
LEVEL_ORDERS_DATA_AND_EDITOR_EXPLANATION.txt.

Reporting packed boxes to the Orders system (Orders feature, Phase 2)
---------------------------------------------------------------------
RetireBox now calls ReportPackedBoxToOrders on the packed branch only, before
the Box is destroyed.

The packed branch is the correct place because it is the same branch that
already plays the completion sound, unlocks adjacent blocked cells, and awards
coins. Removal paths such as the Hammer, and empty transfer sources, retire with
packed=false, so they cannot count toward an order.

The color is read from the still-alive Box through GetDistinctColors. A packed
box is single-colored by definition, so the first distinct color is the box's
color; if that is somehow not true the report is skipped rather than guessing.
The call is made before AwardPackedBox and MovePackedCopyToTruck so the reported
source position is the cell the box actually occupied.

OrderManager.instance is null-checked, so a scene without the Orders system
behaves exactly as it did before. OrderManager itself ignores any color that no
order asks for, which is why packing an unordered box produces no visual at all.

Board's own win-condition call, CheckWinCondition inside AwardPackedBox, is
unchanged in this phase. See ORDERS_RUNTIME_AND_PANEL_EXPLANATION.txt.

Delayed coin burst for order-claimed boxes (Orders feature, Phase 6)
--------------------------------------------------------------------
ReportPackedBoxToOrders now returns whether an order actually claimed the box,
and that result is passed into AwardPackedBox.

When an order claimed it, the CoinManager burst is deferred by
packedCoinVisualDelay (serialized, 0.95 s, set to 0 to restore the old timing).
Two reward animations starting on the same frame competed for attention, and the
order effect is the one that explains why the level is progressing.

Only the burst animation moves. GameDataManager still receives the coins
immediately, so nothing about scoring or the win check changes. A packed box that
no order wanted keeps the original immediate burst.

The wait is unscaled, matching the order effect, which is also unscaled so it can
finish even after an end panel freezes gameplay. See
ORDERS_VISUAL_PARITY_PASS_EXPLANATION.txt.
