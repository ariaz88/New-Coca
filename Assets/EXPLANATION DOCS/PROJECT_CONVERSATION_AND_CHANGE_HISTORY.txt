PART 2 - CLEAN ORGANIZED PROJECT NOTES
======================================

High-level game explanation
---------------------------

This project is a mobile-friendly Unity puzzle/sorting game.
The player receives boxes from a bottom rail and drags them onto a board grid.
Each box can contain soda/items with different colors.
When boxes are placed next to each other, the game checks connected neighbors and transfers/merges matching soda colors.
When enough same-color sodas gather in a valid box, that box completes a match, clears, and rewards progress.

The core genre is:

- Casual puzzle
- Sorting puzzle
- Match/clear puzzle
- Mobile board-and-drag game


Main systems in the game
------------------------

1. Board system

Responsible for creating the grid, tracking active cells, blocked cells, occupied cells, and valid placement positions.
Recent work added per-level board size and custom board shapes.

Important concepts:

- Not every level needs the same width/height.
- Some cells can be removed or blocked.
- Board layout data should live in level configuration, not hardcoded code.
- Gizmos are used to see board cells in the Scene view.


2. Cell/node system

Each board cell represents a possible position for a box.
Cells know whether they are playable, occupied, blocked, or empty.
The board uses these cells to find neighbors and decide where a dragged box can be placed.


3. Box system

Boxes are the main objects the player drags and places.
A box can contain one or more soda/items.
The box has capacity and state.
The system should reuse the existing box capacity and item-color logic instead of inventing duplicate data.


4. Soda/item color system

The game already has a color/type system for sodas/items.
Any new editor setup or initial-box configuration should reuse the existing Soda color enum/data.
Creating a second color system would cause bugs and confusion.


5. Rail spawning system

The bottom rail spawns boxes that the player can drag onto the board.
The rail must keep feeding the player boxes according to the level setup.
Dragging a box from the rail should not change gameplay rules just to fix rendering.


6. Drag-and-drop system

The player drags a box from the rail and drops it onto a valid board cell.
Important rules:

- A dragged box should appear visually above board boxes.
- Placement rules must not change during visual render fixes.
- Box scale and movement should remain the same.
- Rendering priority should be restored after drop or return.


7. Matching and transfer system

The matching system checks connected boxes and moves sodas/items between them.
The latest important design decision:
If a 4-match is possible inside the connected component, the resolver should prioritize the path that completes that match.

Why this matters:
The old greedy logic could make a locally valid transfer that accidentally destroyed the chance of a bigger match.
For example, if the center box is the bridge between left and right boxes, emptying the center too early disconnects the group.

Better behavior:
Search the connected component briefly before choosing the next transfer.
If a short sequence can complete a match of 4, choose the first move from that sequence.
If no match path exists, use the existing greedy behavior as fallback.


8. Tutorial system

The tutorial teaches specific moves using highlights, hand pointer movement, and controlled drag rules.
Important tutorial fixes:

- Hand pointer should stop at the intended cell/target position.
- In tutorial phase two, boxes must be selected in correct order: left, middle, right.
- Out-of-order boxes should not move.


9. Level loading/progression system

The project should not rely blindly on raw Unity build index numbers.
Instead, the game should understand logical levels separately from build indices.

Example:

- Tutorial may be a scene in build index 2.
- Level1 may be build index 3.
- But gameplay should think of them as Tutorial and Level 1, not just raw numbers.

This prevents bugs when new scenes are added or scene order changes.


10. Save and Load system

Save/load data is stored and managed separately from normal gameplay logic.
The relevant scripts were organized under:

Assets/Scripts/Main Scripts/Save and Load

Important issue:
Persistent data like GameDataManager.boxNum must be reset properly for each new level.
If not reset, old level state leaks into the next level and causes wrong win logic.


11. Win and lose system

Win:
The win condition must be guarded so it fires only once.
If multiple matches happen almost at the same time, only one win sequence should run.

Lose:
Game lose should not happen instantly the moment the board becomes full.
The game must first wait for transfer/match/clear resolution after the final placement.
If a match clears space, the player continues.
If no match clears space, then the lose menu appears.

End menu pause:
When win or lose menu appears, gameplay movement should stop.
This includes lift trucks and other active scene movement.


12. Breakable blocked cells

Brown blocked cells are locked cells that cannot accept boxes.
When a matched box is removed, the board checks only direct orthogonal neighbors:

- Up
- Down
- Left
- Right

If a brown blocker is adjacent to the matched box, it should fade/break and then become a normal playable empty cell.

Important rules:

- Only direct neighbors unlock.
- No diagonal unlock.
- No chain reaction.
- No unrelated blockers unlock.
- Animation duration should be configurable in Inspector.


13. Android build and screen adaptation

The game is intended for mobile screens.
For different phone sizes, the board/camera/UI must fit smaller screens than the development test resolution.

Important idea:
The visible gameplay area should be framed according to the screen aspect ratio.
UI should use proper anchors/scaling and should not depend on a single fixed device resolution.

Gradle issue summary:
Android builds are sensitive to Unity version, Android Gradle Plugin version, Gradle wrapper version, JDK version, SDK/NDK versions, and installed Android modules.
When one of these is mismatched, Gradle can fail even if the game code is fine.


14. Unity 6.3 problem

The project experienced severe hangs after upgrading to Unity 6.3 LTS.
The editor got stuck on Application.TickGlobalCallbacks.
Deleting Library and Logs did not solve it.
The user reverted to the previous Unity 6 version.

Lesson:
For this project, Unity 6.3 introduced editor instability.
Future changes should be tested first in the stable Unity version used by the project.


15. Lift truck queue/movement

Problem:
Trucks could stop in the middle of the route or after transferring boxes.

Fix direction:
Truck queue logic needed stronger movement recovery and stable parking alignment.
After correction, parked trucks should face world +X and appear lined up behind each other, as in the original correct layout.


16. Current match-priority lesson

Problem:
The old transfer logic could choose a local move that was legal but strategically wrong.
It might move the center soda away before using it as the bridge for a 4-match.

Required behavior:
If a match of 4 is possible among directly connected boxes, complete that match.
This must work in both:

- Straight-line layouts
- L-shaped connected layouts

Good implementation principle:
Do not rewrite the whole match system.
Keep the current resolver, but add a small deterministic look-ahead before the old greedy fallback.
