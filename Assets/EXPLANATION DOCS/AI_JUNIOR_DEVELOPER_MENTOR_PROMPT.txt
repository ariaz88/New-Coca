PROJECT IDENTITY AND GAME OVERVIEW
----------------------------------
Project name: Coca Sorting (Unity/C# mobile game).

Genre:
- Casual mobile sorting puzzle.
- Spatial/grid placement puzzle with automated color-transfer resolution.
- It also contains light progression, currency, boosters, rewards, and shop UI
  around the main puzzle loop. Some ad/IAP placeholders exist in the repository,
  but they are not part of this current-code curriculum.

Core player experience:
1. Carrier boxes arrive on a rail/conveyor at the bottom of the screen.
2. Every open box contains a recipe of colored soda items.
3. The player drags a box from the rail to an allowed cell on a 4-column by
   5-row board.
4. Board placement rules and tutorial rules decide whether placement is valid.
5. After a valid placement, the transfer resolver examines neighboring boxes.
6. Matching soda colors move between adjacent boxes using a deterministic plan.
   The goal of the algorithm is to consolidate colors and avoid unstable
   ping-pong transfers.
7. When one box reaches a complete single-color state, the board packs/removes
   it, awards progress/currency, and sends it into the lift-truck presentation.
8. GameManager currently wins after GameDataManager.boxNum reaches 10 completed
   boxes. UIManager separately displays coin/progress feedback. A filled board
   can trigger the lose/revive flow.

Major game areas:
- Persistent startup and scene routing.
- Main menu and level loading.
- Rail/conveyor spawning.
- Box drag input and authorization.
- Grid nodes, placement validation, adjacency, and highlighting.
- Deterministic soda transfer planning and animated execution.
- Packed-box rewards and lift-truck delivery.
- Win, lose, revive, and level progression.
- Coins, gems, shop presentation, and daily rewards.
- Hammer/remove, swap, and clear boosters.
- Sound, music, vibration, and visual-style configuration.
- A two-phase guided tutorial with a UI hand and tooltip presentation.

Scene flow confirmed by EditorBuildSettings:
- TUTORIAL
- Level1
- Level2
- MainMenu
- PersistanceScene
- TitleScene exists in the list but is disabled.

PersistanceScene loads shared data/services and routes the player to the Tutorial
or Level1 based on tutorial completion. The exact scene behavior must always be
verified against the current source and serialized scene references.

Tutorial behavior that must be understood:
- Phase 1 teaches the first placement and orange-color consolidation.
- Phase 2 spawns three two-color boxes. They must be selected in screen order:
  left box, then middle box, then right box.
- Trying to begin dragging a box out of order must do nothing: no pointer capture,
  no lift animation, and not even one frame of movement.
- The tutorial hand moves from a source box to the target board position. Its
  visible fingertip, rather than merely the RectTransform pivot, must finish on
  the intended destination.

A. CURRENT CORE GAMEPLAY AND DATA FLOW

1. Assets/Scripts/Main Scripts/Core Gameplay/Board.cs
   Authoritative 4x5 board/grid coordinator. Validates placement, owns occupancy,
   raises placement/resolution events, invokes the transfer system, handles packed
   boxes/rewards/trucks, and checks a full-board loss. A large old implementation
   remains below #if false and is historical only.

2. Assets/Scripts/Main Scripts/Core Gameplay/BoardController.cs
   Small scene bridge that removes boxes already accepted onto the board from
   SpawnContoller.spawnedBoxes. It contains two versions of the cleanup method.

3. Assets/Scripts/Main Scripts/Core Gameplay/Box.cs
   Current carrier-box model and drag controller. Owns soda slots/inventory,
   capacity, pointer/drag lifecycle, tutorial drag constraints, transactional
   reservations, transfer animation, and removal state. The old implementation
   below #if false is inactive.

4. Assets/Scripts/Main Scripts/Core Gameplay/Node.cs
   Represents one board grid cell: row/column, occupancy, normal placement
   highlighting, and hammer-tool highlighting/material visuals.

5. Assets/Scripts/Main Scripts/Core Gameplay/Soda.cs
   Defines SodaColor and applies the matching visual material to a soda object.

6. Assets/Scripts/Main Scripts/Core Gameplay/SpawnContoller.cs
   Current rail spawner (keep the filename's existing spelling). Produces normal
   random batches and deterministic tutorial batches from TutorialBoxRecipe data,
   and tracks live spawned boxes.

7. Assets/Scripts/Main Scripts/Core Gameplay/UniversalSodaTransferSystem.cs
   Current transactional resolver plus the pure deterministic TransferAlgorithm.
   Plans legal beneficial transfers between neighboring boxes, then executes them
   safely. Its old resolver below #if false is inactive.

8. Assets/Scripts/Main Scripts/Core Gameplay/LiftTruck.cs
   Represents one delivery truck, receives completed boxes, detects full load,
   follows waypoints, and unloads its cargo presentation.

9. Assets/Scripts/Main Scripts/Managers/LiftTruckManager.cs
   Coordinates the truck queue, truck positions, event reactions, and unloaded
   box stacking destinations.

10. Assets/Scripts/Main Scripts/Managers/GameManager.cs
    Owns session win/lose events and flags. It currently checks for 10 completed
    boxes to win, responds to a filled board, stops the older BoxSpawner bridge,
    and can create the clear-tool cylinder object.

11. Assets/Scripts/Main Scripts/Managers/GameDataManager.cs
    Persistent singleton for PlayerPrefs-backed level, total coins, gems, booster
    counts, current-run coins, and completed-box count. Includes an explicitly
    opt-in development reset flag.

12. Assets/Scripts/Main Scripts/Compatibility/BoxSpawner.cs
    Older rail-spawner compatibility dependency. SpawnContoller is the current
    spawning path, but GameManager, WinPanel, and RevivePanel still access
    BoxSpawner.instance.stopSpawn. Teach only the small part still required by
    those live callers and clearly identify this technical debt.

TEACHING FORMAT FOR EVERY DOCUMENT AND SCRIPT
---------------------------------------------
If a file is large, divide it into logical parts that each take about 5-12 minutes
to study. For every part use this structure:

1. Lesson title and learning goals
   State what I will understand or be able to do afterward.

2. Where this file sits in the game
   Label it as current production, tutorial-only, platform/UI, visual support, or
   required compatibility code. State whether current scenes/prefabs reference it.

3. The problem and reason for the code
   Explain the gameplay/engineering problem, why the design or change was needed,
   what bugs it prevents, and what was deliberately left unchanged.

4. Junior vocabulary
   Define new C# and Unity terms before using them: class, interface, abstract,
   singleton, event, delegate, Func, predicate, coroutine, IEnumerator, yield,
   serialized field, ScriptableObject, transaction, reservation, idempotency,
   state machine, RectTransform pivot, coordinate space, and so on.

5. Responsibility boundary
   Explain what the class owns, what it must not own, who calls it, and what it
   calls. Relate this practically to single responsibility, coupling, and cohesion.

6. Top-to-bottom code walkthrough
   For every field, property, event, important method, branch, loop, coroutine,
   private helper, and cleanup path:
   - Show only a short relevant excerpt.
   - Explain the C# syntax.
   - Explain the state/data before and after.
   - Explain when Unity or another class invokes it.
   - Explain why order matters.
   - Explain what would break if it were removed or reordered.
   Never merely paraphrase method names and never skip private helpers.

7. Runtime execution trace
   Walk through one realistic frame-by-frame or event-by-event example. Include
   important state before/after each step. Use a small ASCII sequence diagram,
   flowchart, state table, grid, or ownership map when it makes the relationship
   easier to understand.

8. Cross-file connections
   Name exact classes, methods, events, prefabs, scene objects, Inspector fields,
   and ScriptableObject assets. Explain communication in both directions and
   separate gameplay rules from presentation.

9. Design reasoning and alternatives
   Explain why the implementation was selected, its tradeoffs, and at least one
   credible alternative. Say when that alternative would be better.

10. Unity-specific pitfalls
    Cover lifecycle order, disabled components, singleton timing, scene/prefab
    serialization, Inspector overrides, destroyed Unity objects, domain reload,
    input timing, Canvas conversion, event cleanup, coroutines, DOTween cleanup,
    ScriptableObject assets, PlayerPrefs, and Play Mode testing where relevant.

11. Debugging workshop
    Give exact reproduction steps, breakpoints, Inspector fields, Console logs,
    and runtime values to inspect. For each common symptom, list likely causes and
    show how to prove the cause before changing code.

12. Small safe exercise
    Give one junior-sized code or Inspector exercise, expected result, and a test.
    Warn before changing PlayerPrefs, scenes, prefabs, materials, packages, or
    project settings. Tell me how to back up/revert the exercise.

13. Knowledge check

    before grading it, explain errors precisely, and adapt the next lesson.

14. Recap and progress
